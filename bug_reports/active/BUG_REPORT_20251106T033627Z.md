# Bug Report — Docling OCR Memory Risks & Mitigations

Date: 2025-11-06
Timestamp: 2025-11-06T03:36:27Z (UTC)
Author: Codex CLI assistant

## Summary

Upstream reports indicate OCR-related memory regressions/leaks (notably with EasyOCR) in recent Docling versions, causing OOMs in containers during multi-document processing. Our pipeline supports OCR; we should adopt mitigations and consider alternative OCR backends.

## Evidence
- core/docling_adapter.py and core/document_processor.py handle OCR flows; OCR considered expensive.
- requirements.txt references `docling>=0.1.0` (verify actual subpackages used, e.g., docling-parse version).

## Impact
- Potential OOMs/instability when processing large/scanned PDFs or big batches.

## Recommended Fixes
1) OCR policy:
   - Default OCR off for programmatic PDFs; detect scans first.
   - Allow user toggle per run.
2) Alternative OCR backend:
   - Prefer RapidOCR over EasyOCR in containers; expose config to switch.
3) Chunking & cleanup:
   - Process pages in batches for long docs; explicitly free intermediate results.
4) Version pinning:
   - Pin Docling packages to versions with known fixes; document memory behavior.

## Validation Steps
1) Run batch with mixed documents; monitor RSS; confirm no unbounded growth.
2) Test chunked processing on long documents; verify stable memory.
