## Critical Issues

### 1. Security Vulnerability - Development JWT Secret (CRITICAL) ✅ RESOLVED
**Location:** `api/auth.py:22-29`

**Issue:** System falls back to insecure development JWT secret when `JWT_SECRET_KEY` is not set, with only a warning log.

**Impact:** Production deployments without proper environment configuration use predictable JWT secrets, allowing token forgery.

**Evidence:**
```python
if not SECRET_KEY:
    SECRET_KEY = "dev-secret-CHANGE-IN-PRODUCTION"  # CRITICAL SECURITY ISSUE
    logger.warning("⚠️  Using insecure development JWT secret...")
```

**RESOLUTION (commit 4efdebb):**
- Added APP_ENV environment variable check
- Development mode allows fallback with warning (lines 27-34)
- Production/staging mode raises ValueError if JWT_SECRET_KEY not set (lines 36-41)
- Fail-fast behavior with clear error message
- Updated docker-compose.yml to set APP_ENV=development

### 2. Missing Dependencies / Import Resolution (CRITICAL) ⚠️ FALSE POSITIVE

## High Severity Issues

### 4. Missing Error Handling in Event Processor (HIGH) ✅ RESOLVED
**Location:** `api/event_processor.py:95-99`

**Issue:** Event processor catches all exceptions but only logs them, potentially silently failing to update run/document states.

**Impact:** Worker events may be lost, causing inconsistent state between worker and API.

**RESOLUTION (commit d58290d):**
- Implemented 3-attempt retry mechanism with exponential backoff (1s, 2s, 4s)
- Added Dead Letter Queue (DLQ) in Redis for permanently failed events
- Events that fail after all retries are preserved in DLQ for manual recovery
- Comprehensive logging of retry attempts and DLQ movements

### 5. SQLAlchemy ORM Assignment Issues (HIGH) ⚠️ TYPE-CHECKING WARNING
**Location:** Multiple files (api/main.py, api/event_processor.py, worker/tasks_refactored.py)

**Issue:** Direct assignment to SQLAlchemy Column attributes instead of using proper ORM patterns.

**RESOLUTION:**
- These are type-checking warnings from static analysis tools
- Runtime behavior is correct and working as expected
- SQLAlchemy ORM supports direct attribute assignment

## Medium Severity Issues

### 6. Missing Input Validation (MEDIUM) ✅ RESOLVED
**Location:** `api/main.py:523-557` (get_run_events endpoint)

**Issue:** No validation on `cursor` and `limit` parameters, potentially causing performance issues.

**Impact:** Large limit values could cause memory exhaustion or database performance degradation.

**RESOLUTION (commit 253b505):**
- Added FastAPI Query validators to list_clients endpoint (lines 204-205)
- Added FastAPI Query validators to get_run_events endpoint (lines 531-532)
- cursor: ge=0 (must be non-negative)
- limit: ge=1, le=1000 (must be between 1 and 1000)

### 8. Missing Health Check Timeouts (MEDIUM) ✅ RESOLVED
**Location:** `infra/storage.py:362-376`

**Issue:** MinIO health check has no timeout, could hang API startup.

**RESOLUTION (commit bd31b7a):**
- Added urllib3 Timeout configuration to MinIO client
- Default: 10s connect, 30s read (configurable via MINIO_TIMEOUT_SECONDS)
- Added timeout_handler context manager to health_check method
- Default health check timeout: 5 seconds
- Prevents API startup hangs on MinIO network issues

### 10. Docker Container Resource Limits (LOW) ✅ RESOLVED
**Location:** `docker-compose.yml`

**Issue:** No memory or CPU limits defined for containers, potentially causing host resource exhaustion.

**RESOLUTION (commit a8caf1a):**
- Added deploy.resources.limits to all 6 services:
  - postgres: 2 CPU / 2GB RAM (limits), 0.5 CPU / 512MB RAM (reservations)
  - redis: 1 CPU / 512MB RAM (limits), 0.25 CPU / 128MB RAM (reservations)
  - minio: 2 CPU / 1GB RAM (limits), 0.5 CPU / 256MB RAM (reservations)
  - api: 2 CPU / 2GB RAM (limits), 0.5 CPU / 512MB RAM (reservations)
  - worker: 4 CPU / 4GB RAM (limits), 1 CPU / 1GB RAM (reservations)
  - frontend: 0.5 CPU / 256MB RAM (limits), 0.1 CPU / 64MB RAM (reservations)
