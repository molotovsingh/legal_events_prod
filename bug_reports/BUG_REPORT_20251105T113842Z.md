# Bug Report — Worker Mutates API‑Owned Entities (Runs/Documents)

Date: 2025-11-05
Timestamp: 2025-11-05T11:38:42Z (UTC)
Author: Codex CLI assistant

## Summary

Per `CLAUDE.md` guardrails, the Worker should be read‑only for Clients/Cases/Runs/Documents and write‑only for Events/Artifacts. The current Worker modifies `runs` and `documents` (status, timings, errors), violating the service boundary.

## Evidence (current code)
- File: `worker/tasks.py`
  - `run.status = RunStatus.PROCESSING` (line ~58)
  - `doc.status = DocumentStatus.PROCESSING` (line ~90)
  - `doc.status = DocumentStatus.SUCCESS` / `FAILED` (lines ~154, ~165)
  - `run.status = final_status` (line ~187)
  - `run.run_metadata = { ... }` (line ~195)

## Impact
- Erodes microservice boundary; business state for Runs/Documents is owned by API.
- Makes retries and idempotency harder to reason about across services.
- Increases coupling and risk of conflicting updates.

## Recommended Fixes

1) Move state transitions to API
   - Worker publishes progress to Redis (job meta or a progress channel) or writes Events only.
   - API updates `runs` and `documents` via internal endpoints or a background scheduler consuming progress messages.

2) Minimal interim option (if shared DB must stay)
   - Define strict list of allowed columns Worker can update (e.g., none for `runs`/`documents`).
   - Create API endpoints: `/internal/runs/{id}/status`, `/internal/documents/{id}/status` that the Worker calls.

3) CI guard
   - Add import-linter rule forbidding the Worker from importing ORM model classes that are API‑owned, unless moved to a shared `infra/models` package with explicit ownership tags.

## Validation Steps
1) Implement API endpoints or progress consumer to update runs/documents.
2) Adjust Worker to emit progress without mutating runs/documents.
3) Run end‑to‑end: Start a run, verify statuses update via API only; Worker writes only Events/Artifacts.
