# Bug Report — Cross‑Imports Violate Guardrails (API ↔ Worker)

Date: 2025-11-05
Timestamp: 2025-11-05T11:36:53Z (UTC)
Author: Codex CLI assistant

## Summary

The Worker service imports `api.*` modules directly. This violates the guardrails documented in `CLAUDE.md` ("No Cross-Imports") and couples services at the module level. It makes boundaries porous and complicates independent deployment and testing.

## Evidence
- File: `worker/tasks.py`
  - Imports: `from api.models import ...`, `from api.storage import MinioStorage`, `from api.queue import JobProgress` (and related usage).
- Rule in `CLAUDE.md` → Import Rules:
  - NEVER: `from worker import ...` in API code
  - NEVER: `from api import ...` in Worker code
  - ALWAYS: Use Redis/DB for cross-service communication; share only common libraries.

## Impact
- Service boundary erosion; Worker depends on API package internals.
- Higher risk of circular dependencies and accidental behavior changes across services.
- Harder to evolve or scale services independently.

## Recommended Fixes

1) Extract shared code into a neutral package (e.g., `infra/` or `common/`)
   - Move shared components out of `api/` into `infra/`:
     - SQLAlchemy models: `api/models.py` → `infra/models.py` (or a models package)
     - Database session factory: `api/database.py` → `infra/database.py`
     - Storage client: `api/storage.py` → `infra/storage.py`
     - Queue utilities: `api/queue.py` → split into `infra/queue.py` (pure RQ helpers)
   - Update API and Worker to import from `infra.*` only.

2) Enforce string-based RQ enqueues (API → Worker)
   - Use `queue.enqueue("worker.tasks.process_run", ...)` to avoid importing worker code in API.
   - Confirm current code adheres; add an import-linter check in CI.

3) Add import rules to CI
   - Introduce `import-linter` (or a simple grep) to block `from api import` in `worker/` and `from worker import` in `api/`.

4) Document boundary
   - Update `CLAUDE.md` with concrete examples of allowed imports and directory layout for `infra/`.

## Validation Steps
1) Create `infra/` and move shared modules; run `alembic` and boot the stack.
2) Ensure API starts and worker processes runs without referencing `api.*` from worker.
3) Run a test extraction; verify events and artifacts are produced.
4) Run import-linter in CI to enforce no cross-imports.

## Notes
- Keeping `core/` as a shared dependency is fine. For reproducibility, consider packaging `core/` as a wheel and pinning the version in each service.
