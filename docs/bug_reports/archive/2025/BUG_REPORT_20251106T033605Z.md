# Bug Report — Alembic Enum Migration Strategy (PostgreSQL, SQLAlchemy 2.x)

Date: 2025-11-06
Timestamp: 2025-11-06T03:36:05Z (UTC)
Author: Codex CLI assistant

## Summary

The project uses native PostgreSQL enums (e.g., `userrole`, `runstatus`, `documentstatus`, `clientstatus`, `casestatus`). Renaming enum values or changing sets requires explicit strategies; Alembic autogenerate won’t handle value renames safely.

## Evidence
- migrations/versions/001_initial_schema.py: creates multiple enum types.
- api/models.py: uses `Enum(..., native_enum=True)`.

## Impact
- Ad-hoc enum changes can break migrations or require non-transactional operations.

## Recommended Fixes
1) Adopt a standard enum migration pattern:
   - Convert column to TEXT; update values; create new enum; cast back; drop old type (transactional approach).
   - Or use helper libraries (`alembic-postgresql-enum`, `alembic-enums`) for safer value sync/rename.
2) Document the process:
   - Add a short doc under `docs/` describing enum changes with examples.

## Validation Steps
1) Prototype a value rename (e.g., `partial` → `partial_success`) in a feature branch following the pattern.
2) Upgrade + downgrade locally; verify integrity and `SELECT` checks.
